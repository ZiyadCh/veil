Relations JPA : unidirectionnelle et bidirectionnelle

Fil rouge : un Client possède plusieurs Commande. Au programme : navigation, base de données, JSON, chargement, cascade, orphanRemoval, bonnes pratiques.

1. Définitions

Unidirectionnelle

Une seule entité connaît l’autre : une seule référence Java.

@Entity
public class Commande {
  @Id @GeneratedValue
  private Long id;

  @ManyToOne
  @JoinColumn(name = "client_id")
  private Client client;
}
// Client ne connaît pas ses commandes

Bidirectionnelle

Les deux entités se connaissent : une référence dans chaque classe.

@Entity
public class Client {
  @Id @GeneratedValue
  private Long id;
  private String nom;

  @OneToMany(mappedBy = "client")
  private List<Commande> commandes
      = new ArrayList<>();
}
// Commande reste inchangée

2. Sens de navigation : qui connaît qui ?

On navigue de A vers B uniquement si A possède un attribut (et un getter) vers B.

RelationNavigation possible
Unidirectionnelle Commande → Clientcommande.getClient() ✅
client.getCommandes() ❌ n’existe pas
Bidirectionnellecommande.getClient() ✅ et client.getCommandes() ✅
Commande c = commandeRepository.findById(1L).orElseThrow();
String nom = c.getClient().getNom();      // Commande → Client

Client cl = clientRepository.findById(1L).orElseThrow();
int nb = cl.getCommandes().size();        // bidirectionnel seulement

Sans navigation Client → Commandes : passer par une requête, commandeRepository.findByClientId(id).

3. Impact sur la base de données

Schéma identique dans les deux cas

CLIENT   (id, nom)
COMMANDE (id, client_id → FK CLIENT.id)

Passer en bidirectionnel n’ajoute aucune colonne, seulement un attribut Java.

Côté propriétaire

Celui qui contrôle la clé étrangère : JPA ne lit que lui pour écrire. Ici, c’est le côté @ManyToOne.

Rôle de mappedBy

Placé côté inverse pour dire à JPA de ne pas créer un second mapping. Explication détaillée à la diapositive suivante.

Piège : seul le côté propriétaire est persisté. Synchroniser les deux côtés : 
public void addCommande(Commande c) {
  commandes.add(c);
  c.setClient(this);   // c’est ce côté qui écrit la FK
}

mappedBy en une page

En bidirectionnel, il y a deux attributs Java mais une seule clé étrangère. mappedBy indique à JPA que les deux attributs décrivent la même relation et que l’autre côté est chargé de l’écrire en base.

Le code

// Client (côté inverse)
@OneToMany(mappedBy = "client")
private List<Commande> commandes;

// Commande (côté propriétaire)
@ManyToOne
@JoinColumn(name = "client_id")
private Client client;   // ← "client"

La valeur de mappedBy est le nom de l’attribut Java de l’autre classe, pas une colonne.

Ce qui se passe

  • Démarrage : Hibernate retrouve l’attribut client dans Commande et réutilise son mapping. Aucune colonne ni table en plus.
  • Lecture : client.getCommandes() lance SELECT ... FROM commande WHERE client_id = ?.
  • Écriture : seule Commande.client alimente client_id. Le contenu de la liste est ignoré.

Sans mappedBy

Hibernate voit deux relations indépendantes et crée une table de jointure inutile client_commandes, en plus de commande.client_id.

Règles

  • Toujours côté inverse (@OneToMany), jamais sur le @ManyToOne.
  • Un nom incorrect fait échouer le démarrage.
  • Il ne gère ni cascade ni chargement.
Piège : client.getCommandes().add(c) seul laisse client_id = NULL, sans erreur. Il faut aussi c.setClient(client), d’où les méthodes addCommande / removeCommande.

4. Sérialisation JSON : le problème

Avec une relation bidirectionnelle, chaque entité référence l’autre. Quand un contrôleur renvoie un Client, Jackson parcourt le graphe via les getters :

  1. Il sérialise Client : il a commandes, donc il sérialise chaque Commande.
  2. Il sérialise une Commande : elle a client, donc il sérialise le Client.
  3. Ce Client a commandes… et la boucle recommence.

Jackson ne sait pas qu’il a déjà visité ces objets. Résultat : StackOverflowError ou HttpMessageNotWritableException (« Infinite recursion »), avec une longue trace qui répète Client et Commande.

Ce que Jackson tente d’écrire : les mêmes objets reviennent à chaque niveau, sans jamais s’arrêter.

{
  "id": 1, "nom": "Alami",
  "commandes": [{
    "id": 10,
    "client": {                  // le même Client
      "id": 1, "nom": "Alami",
      "commandes": [{            // la même Commande
        "id": 10,
        "client": { ... }        // et ainsi de suite
      }]
    }
  }]
}

Seulement en bidirectionnel

En unidirectionnel Commande → Client, la sérialisation s’arrête au Client, qui n’a pas de chemin de retour.

Problème lié : le lazy loading

Client.commandes est LAZY. Si Jackson sérialise après la fin de la transaction (cas typique), getCommandes() lève une LazyInitializationException. Renvoyer directement des entités reste fragile même sans boucle.

Sérialisation JSON : la solution par DTO

Un DTO est une classe simple, distincte de l’entité, qui décrit exactement ce que l’API renvoie. On mappe l’entité vers le DTO et on renvoie le DTO.

public record CommandeDto(Long id, LocalDate date, Long clientId) {}
public record ClientDto(Long id, String nom, List<CommandeDto> commandes) {}

CommandeDto porte clientId (un Long), pas un objet Client : le graphe est un arbre, sans cycle.

JSON obtenu : l’imbrication s’arrête après un niveau.

{
  "id": 1, "nom": "Alami",
  "commandes": [
    { "id": 10, "date": "2026-10-19", "clientId": 1 }
  ]
}

Le mapping se fait dans la couche service, tant que la transaction est ouverte :

public ClientDto toDto(Client c) {
  List<CommandeDto> cmds = c.getCommandes().stream()
    .map(cmd -> new CommandeDto(cmd.getId(), cmd.getDate(), c.getId()))
    .toList();
  return new ClientDto(c.getId(), c.getNom(), cmds);
}

Ce que cela résout

  • Pas de boucle : la structure est un arbre.
  • Pas d’exception lazy : la collection est lue dans le service, session ouverte.
  • Sortie maîtrisée : un champ sensible ajouté à l’entité ne fuit pas dans l’API.

Autres avantages

  • Découplage : le modèle de persistance peut évoluer sans casser l’API.
  • Forme par cas d’usage : un ClientSummaryDto léger pour les listes, un ClientDto complet pour le détail.

Coût : du code de mapping, réductible avec MapStruct.

5. Chargement : LAZY vs EAGER

Le fetch type décide quand JPA charge l’entité associée.

LAZYEAGER
ChargementÀ la première utilisation de la relationTout de suite, avec le parent
AvantageOn ne charge que ce qui sertDonnées déjà disponibles, même hors transaction
RisqueLazyInitializationExceptionGraphes inutiles, requêtes en cascade

Valeurs par défaut

  • @ManyToOne, @OneToOne : EAGER
  • @OneToMany, @ManyToMany : LAZY
@ManyToOne(fetch = FetchType.LAZY)
private Client client;

Comment fonctionne LAZY

Hibernate injecte un proxy (ou une collection spéciale) à la place des vraies données. Le premier accès (getNom(), size()) déclenche un SELECT, à condition que la session soit encore ouverte.

LazyInitializationException

Accès à une relation LAZY après la fin de la transaction (souvent à la sérialisation). Solutions : lire dans une méthode @Transactional du service, charger avec JOIN FETCH/@EntityGraph, ou mapper en DTO dans le service.

EAGER : piège

findById charge l’association avec une jointure, mais une requête JPQL ou findAll() ignore le EAGER et lance une requête de plus par ligne. EAGER ne protège donc pas du N+1 et ne se désactive pas au cas par cas.

Chargement : le problème N+1 et ses solutions

On charge 100 commandes, puis on lit getClient().getNom() sur chacune : 1 requête pour les commandes + 100 requêtes pour les clients.

List<Commande> cs = commandeRepository.findAll();   // 1 requête
for (Commande c : cs)
    System.out.println(c.getClient().getNom());      // + N requêtes

JOIN FETCH

@Query("SELECT c FROM Client c
        JOIN FETCH c.commandes
        WHERE c.id = :id")
Optional<Client> findByIdWithCommandes(Long id);

Une seule requête avec jointure.

@EntityGraph

@EntityGraph(attributePaths = "client")
List<Commande> findAll();

Même effet, sans écrire de JPQL.

Limites : JOIN FETCH d’une collection avec pagination force Hibernate à paginer en mémoire ; charger deux collections List à la fois lève MultipleBagFetchException. Alternatives : deux requêtes, ou @BatchSize.

Règle : LAZY partout, puis charger explicitement par requête ce dont chaque cas d’usage a besoin.

6. CascadeType : propager les opérations

Par défaut, une opération sur le parent ne touche pas les entités associées. cascade la propage aux enfants.

TypeEffet
PERSISTpersist(parent) persiste aussi les enfants nouveaux
MERGEmerge(parent) fusionne aussi les enfants
REMOVEremove(parent) supprime aussi les enfants
REFRESH / DETACHRecharge / détache aussi les enfants
ALLTous les types ci-dessus

Avec cascade

@OneToMany(mappedBy = "client",
           cascade = CascadeType.ALL)
private List<Commande> commandes;

Client cl = new Client("Alami");
cl.addCommande(new Commande());
clientRepository.save(cl);  // INSERT client + commande

Sans cascade

Chaque enfant doit être géré à la main, dans le bon ordre.

Client cl = new Client("Alami");
Commande cmd = new Commande();
cl.addCommande(cmd);

clientRepository.save(cl);      // INSERT client
commandeRepository.save(cmd);   // obligatoire : INSERT commande
// sans cette ligne : exception au flush
// (« object references an unsaved transient instance »)

Même chose à la suppression :

// delete(cl) seul : violation de clé étrangère
commandeRepository.deleteAll(cl.getCommandes());
clientRepository.delete(cl);
À retenir : la cascade exprime un cycle de vie partagé (une Commande n’existe pas sans son Client), pas un raccourci de sauvegarde. Sur un @ManyToOne vers une entité partagée, elle est presque toujours une erreur : supprimer une commande supprimerait son client. REMOVE sur un @ManyToMany est tout aussi dangereux.

7. orphanRemoval : le principe

Un enfant est orphelin quand il n’est plus dans la collection de son parent. Avec orphanRemoval = true, JPA le considère comme sans raison d’exister et le supprime de la base.

@OneToMany(mappedBy = "client", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Commande> commandes = new ArrayList<>();

Situation de départ : le client 1 a trois commandes (10, 11, 12). On retire la 11.

Client client = clientRepository.findById(1L).orElseThrow();
Commande c = client.getCommandes().get(1);   // commande 11
client.removeCommande(c);                    // retire de la liste + setClient(null)
// fin de la transaction (flush)

Avec orphanRemoval

DELETE FROM commande WHERE id = 11

Il reste les commandes 10 et 12.

Sans orphanRemoval

UPDATE commande SET client_id = NULL
WHERE id = 11

La commande 11 reste en base, sans client (ou erreur si client_id est NOT NULL).

Pourquoi un mécanisme à part ? Retirer un élément d’une liste Java ne supprime rien : JPA n’a aucune raison de deviner qu’il faut effacer la ligne. orphanRemoval lui dit de surveiller la collection et de supprimer ce qui en sort.

orphanRemoval : cas, conditions et pièges

Ce que fait le codeSans orphanRemovalAvec orphanRemoval
client.removeCommande(c) (liste + setClient(null))UPDATE client_id = NULLDELETE de la commande
client.getCommandes().remove(c) seulRien en base (côté inverse)DELETE de la commande
c.setClient(null) seul, c encore dans la listeUPDATE client_id = NULLPas de suppression : c n’a pas quitté la collection
clientRepository.delete(client)Erreur de clé étrangère, sauf REMOVELes commandes sont supprimées aussi
client.setCommandes(new ArrayList<>())Aucun effet en baseException : « A collection with cascade="all-delete-orphan" was no longer referenced »

Conditions

  • Disponible sur @OneToMany et @OneToOne.
  • Le parent doit être géré (dans une transaction).
  • Le DELETE part au flush, pas à l’appel de remove.

Quand l’utiliser

  • Le parent est propriétaire exclusif de l’enfant (commande et lignes).
  • Jamais si l’enfant peut être rattaché ailleurs ou réutilisé.
  • Pour changer la liste : clear(), remove(), add() sur la collection existante.
Différence avec REMOVE : REMOVE se déclenche quand on supprime le parent ; orphanRemoval quand on retire un enfant de la collection. On les combine pour une vraie composition.

8. Bonnes pratiques : choisir le sens de la relation

Question à se poser : de quel côté mon code a-t-il vraiment besoin de naviguer ?

BesoinChoix
Atteindre le parent depuis l’enfant (commande.getClient())Unidirectionnelle @ManyToOne
Parcourir les enfants depuis le parent (commande.getLignes()) avec cascade et orphelinsBidirectionnelle
Collection énorme (milliers d’éléments)Pas de @OneToMany ; requête paginée : commandeRepository.findByClientId(id, pageable)

Exemple : une commande et ses lignes

// Composition : bidirectionnel + cascade
Commande 1 <-> * LigneCommande
  cascade = ALL, orphanRemoval = true

// Référence : unidirectionnel, sans cascade
LigneCommande * -> 1 Produit
  @ManyToOne(fetch = LAZY)

Pourquoi rester simple

Chaque direction ajoute de la complexité : synchronisation des deux côtés, mappedBy, boucles JSON, equals/hashCode/toString. On peut ajouter l’autre côté plus tard sans changer le schéma SQL.
